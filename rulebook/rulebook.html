1. Document layout

How yamkix lays out every YAML document it writes: the start and end markers, how lists are indented, whether collections are written in flow (JSON-like) or block style, where long lines are folded, and the clean-up of trailing spaces. These are the house-style choices of the formatter; they are meant not to change the data a document holds (see LAY-R010.E3 for one exception).

Covers
explicit start --- and end ... markers, dash pushed inwards (mapping 2 / sequence 4 / offset 2 indentation), default flow style, forcing block style on JSON-like collections, line width, stripping trailing spaces and the leading double space of top-level lists.
Concepts
document, explicit start, explicit end, dash inwards, flow style, block style, empty collection, line width, round-trip (rt) vs safe parsing mode.

LAY-R003

List dashes are pushed inwards by default

By default, the items of a list nested under a key are indented by 2 spaces, the dash sits 2 spaces in from the key, and the item content 4 spaces in; nested maps are indented by 2 spaces.

This is yamkix's main opinion and matches what yamllint expects by default. The three values are fixed in the code and cannot be changed by an option.

A document that is a list keeps its dashes at column 0

When a whole document is a list and dashes are pushed inwards, its top-level dashes are written at column 0 and the rest of the document is shifted 2 spaces left to match.

LAY-R006

Default flow style only shapes collections that have no style of their own

Collections are written in block style by default; --default-flow-style switches to flow style only collections whose style the parser did not record, which in round-trip mode means it has almost no visible effect, while in safe mode the whole document is written in flow style.

In round-trip mode each collection keeps the style it had in the input, so a flow list stays flow and a block map stays block whatever this option says. The safe parser keeps no style, so the option applies everywhere.

With --enforce-block-style in round-trip mode, every map and list of the document, at any depth, is written in block style, except empty ones, which stay [] and {}.

LAY-R008

--enforce-block-style wins over --default-flow-style

In round-trip mode, when both --enforce-block-style and --default-flow-style are given, every non-empty collection is written in block style, and a warning says so.

The precedence comes from the order of operations: each collection is explicitly marked block before dumping, so the default style never applies. In safe mode the warning is printed but the output is flow style (LAY-R007.E3).

LAY-R009

Lines are folded at 2048 characters by default

Long plain values and flow collections are folded onto several lines once a line would exceed 2048 characters, or the width given with --line-width.

LAY-R010

No output line ends with a space

Every line yamkix writes has its trailing spaces removed, whatever the options.

Works around the YAML library leaving a space where it folds a line (issue #437). Values whose trailing space is escaped inside double quotes are safe, but the stripping also runs inside literal blocks (|), where trailing spaces are part of the value: there it changes the data (E3).

Edge cases
  • Given the issue-437 file, when it is formatted with --line-width 80, then the folded lines have no trailing space.
  • Given quoted: "line one \nline two" with an escaped line break after a space, when the trailing spaces are stripped, then the value is unchanged.
  • Given a literal block s: | whose first line is a followed by two spaces, when it is formatted, then the two spaces are removed and the loaded value changes from "a \nb\n" to "a\nb\n".

2.1 A quoted value keeps its type

Business policy Removing quotes must never turn a string into a number, a boolean or another type.

QUO-R002

Without quote preservation, only the quotes a value needs are kept, as single quotes

With --no-quotes-preserved, quotes around plain strings are removed, and strings that would otherwise read as another type (such as "1.722" or "true") are written with single quotes.

The YAML library decides which values need quotes; yamkix only switches off the memory of the original quotes. Keys are handled the same way.

2.2 Other operating rules

QUO-R001

Quotes are kept as written by default

By default, in round-trip mode, every quoted value and key keeps its quotes and their kind (single or double), and unquoted values stay unquoted.

In safe mode the original quotes are not remembered, so the output behaves as with --no-quotes-preserved (E2).

QUO-R003

--enforce-double-quotes turns the remaining single quotes into double quotes

With both --no-quotes-preserved and --enforce-double-quotes in round-trip mode, every value still quoted after quote removal is written with double quotes instead of single quotes, including list items.

Done in a second pass on each document: dump it once without the original quotes, read the result back with quotes remembered, swap single-quoted values for double-quoted ones, then dump again. In safe mode the second read keeps no quote kind, so nothing is converted (E3).

3.1 Formatting keeps the author's comments

Business policy Reformatting a YAML file must not lose or move the comments its author wrote.

CMT-R001

Comments are kept in round-trip mode and dropped in safe mode

Comments are kept only when the parsing mode is rt (the default); with --typ safe every comment is removed from the output.

The parsing mode chosen by the user is handed as is to the YAML library; the safe loader does not keep comments. The --typ help text warns about it. Safe mode also rewrites JSON-style collections in block style.

Edge cases
  • Given a file with end-of-line and full-line comments, when it is formatted with --typ safe, then the output holds no comment at all.

CMT-R002

Without a spacing option, comments keep their original column

When --spaces-before-comment is not given, end-of-line comments are written at the same column as in the input, so the gap before a comment grows or shrinks when the value before it is reformatted.

Comment repositioning only runs when a number of spaces was given; otherwise the YAML library re-emits each comment at its original column. --align-comments is a separate option and can still move them (CMT-R005).

3.2 Other operating rules

CMT-R003

A fixed number of spaces is put before every end-of-line comment

With --spaces-before-comment N, every end-of-line comment of a map or a list is written exactly N spaces after its content; a value of 0 gives one space.

The comment is re-added with N − 1 extra spaces in front of it, at column 0; for 0 nothing is added and the library still writes one separating space. Full-line comments are not re-spaced.

Parameters --spaces-before-comment / -c — src/yamkix/_cli.py:179-188 (no default: comments left as is)

Edge cases
  • Given the issue-11 file with comments one to four spaces after their value, when it is formatted with --spaces-before-comment 2, then every comment is two spaces after its value.
  • Given the same file, when it is formatted with --spaces-before-comment 0, then every comment is one space after its value, as with 1.
  • Given a commented line followed by a full-line comment (b: 22 # c2 then # full line), when it is formatted with --spaces-before-comment 1, then the full-line comment is glued to the previous comment (b: 22 # c2# full line).
  • Given both --align-comments and --spaces-before-comment 1, when a file is formatted, then the fixed spacing wins and comments are not aligned.

CMT-R005

Comments of a map are aligned on its rightmost comment

With --align-comments, the end-of-line comments of each map are moved to the column of the rightmost comment of that same map; each map is aligned on its own.

The target column is the rightmost comment already present, not "longest value plus one space": a comment pushed far right in the input pulls the others with it. List items are not aligned in practice (E2).

4.1 A file the user cannot recover is never damaged on purpose

Business policy A file that cannot be formatted must be left as it was.

FIL-R008

A file with a YAML syntax error is reported, left untouched, and the run goes on

When a file has a YAML syntax error (scanner or parser error), yamkix prints an error naming it, does not write its output, counts it as an error, goes on with the next file, and still ends with exit code 0.

The whole input is parsed before the output is opened, so a syntax error can never truncate the file. Other invalid YAML, such as a duplicate key or an undefined alias, is not caught here and stops the run (FIL-R009).

Edge cases
  • Given a changed file and a file containing key: [, when both are formatted with --list-modified --summary, then the first is rewritten and listed, the second keeps key: [, the summary says 2 file(s) processed, 1 error(s) and the exit code is 0.
  • Given a file with a duplicate key (a: 1 then a: 2) followed by a valid file, when both are formatted, then the run stops with a traceback and the second file is not formatted.

FIL-R010

The output file is emptied before it is rewritten

Once the input is parsed, an existing output file is emptied, then each document is appended to it one by one; if writing fails halfway, the file is left partly written.

There is no temporary file and no backup: an in-place run that fails after the truncation (disk full, permission change) loses the original content. --list-modified still reports such a file (FIL-R013).

Edge cases

FIL-R011

A file is "unchanged" only if the output bytes equal the input bytes

A file counts as unchanged in the summary only when the bytes yamkix would write, with the platform's line endings, are identical to the input bytes; for STDIN the text is compared.

FIL-R012

An output counts as modified when it is created or its bytes change

An output file counts as modified when it did not exist, when its new bytes differ from its previous bytes, or when its previous content could not be read; standard output and special files such as /dev/null never count.

OPT-R002

The Python API overrides only the values it is given

get_yamkix_config_from_default builds a configuration where every value not given (left to None) takes its default from OPT-R001, and input and output default to STDIN and STDOUT.

OPT-R004

Safe mode re-emits the data, not the document

With --typ safe, the output is rebuilt from the data alone: comments are dropped, original quotes and collection styles are forgotten, map keys are sorted alphabetically and literal blocks (|) become quoted strings.

The parser mode is handed as is to the YAML library; only round-trip mode keeps the shape of the input. The per-topic effects are carded in CMT-R001, QUO-R001 and LAY-R006.

Edge cases
  • Given keys k1, l, n, b in that order with b: | holding 'x', when formatted with --typ safe, then b comes first and is written b: "'x'\n".
